# 수업 발표 자료 (40분 / 20페이지)

## 발표 기본 정보

- 주제: **PRD 기반 블로그 플랫폼 설계와 구현**
- 대상: 웹개발/소프트웨어공학 수강생
- 총 시간: 40분
- 총 페이지: 20페이지 (슬라이드 20장)
- 권장 진행: 페이지당 평균 2분

---

## 페이지 1. 강의 제목과 목표 (2분)

### 슬라이드 내용

- PRD란 무엇인가?
- 요구사항을 어떻게 구현으로 연결하는가?
- 블로그 플랫폼 사례로 역할/권한 모델 이해

### 발표 멘트

"오늘은 PRD 문서를 단순 문서가 아니라 실제 개발의 출발점으로 보는 관점으로 설명하겠습니다. 특히 우리 프로젝트에서 어떻게 요구사항이 DB, 백엔드, 화면까지 연결되었는지 보겠습니다."

---

## 페이지 2. 왜 PRD가 필요한가? (2분)

### 슬라이드 내용

- 요구사항 누락/오해 방지
- 팀 간 공통 언어 제공
- 테스트 기준(수용 기준) 제공

### 발표 멘트

"많은 팀이 코드부터 시작하다가 '원래 뭘 만들려 했는지'를 잃습니다. PRD는 목표와 범위를 고정해주는 기준선입니다."

---

## 페이지 3. PRD의 핵심 구성요소 (2분)

### 슬라이드 내용

- 문제 정의
- 목표와 범위(In/Out Scope)
- 사용자 역할/시나리오
- 기능/비기능 요구사항
- 수용 기준과 성공 지표

### 발표 멘트

"PRD는 상세 설계서가 아니라 제품의 방향 문서입니다. 무엇을 왜 만드는지, 그리고 무엇으로 성공을 판단할지를 정의합니다."

---

## 페이지 4. 프로젝트 배경: 블로그 플랫폼의 운영 문제 (2분)

### 슬라이드 내용

- 관리자 권한 남용 위험
- 멤버/관리자 경계 불명확
- 업로드 정책 부재로 운영 비용 증가
- 승인 절차 미흡

### 발표 멘트

"교육용 서비스라도 운영 정책이 없으면 금방 무너집니다. 그래서 권한 모델과 승인 흐름이 핵심 요구사항이 됩니다."

---

## 페이지 5. 목표 사용자와 이해관계자 (2분)

### 슬라이드 내용

- 슈퍼관리자: 정책 통제자
- 블로그관리자: 블로그 운영자
- 블로그멤버: 콘텐츠 소비/작성자
- 강사/조교: 품질/학습 성과 검증자

### 발표 멘트

"같은 기능도 사용자마다 기대가 다릅니다. PRD는 역할별 기대를 분리해 다뤄야 합니다."

---

## 페이지 6. 역할 모델: RBAC 설계 (2분)

### 슬라이드 내용

- `SUPER_ADMIN`
- `BLOG_ADMIN`
- `BLOG_MEMBER`
- 승인 상태: `is_approved`

### 발표 멘트

"이번 프로젝트 핵심은 역할 기반 접근제어(RBAC)입니다. 역할과 승인 상태가 결합되면서 실제 권한이 결정됩니다."

---

## 페이지 7. 로그인/회원가입 요구사항 정리 (2분)

### 슬라이드 내용

- 이메일 로그인
- 카카오 OAuth 로그인
- 가입 유형 선택(관리자 신청/멤버 가입)
- 관리자 신청자는 승인 대기

### 발표 멘트

"로그인 방식은 2개지만, 가입 이후의 상태 전이가 더 중요합니다. 특히 관리자 신청은 즉시 권한 부여가 아니라 승인 대기여야 합니다."

---

## 페이지 8. 권한 시나리오: 로그인 후 라우팅 (2분)

### 슬라이드 내용

- `SUPER_ADMIN` -> 관리자 대시보드
- 승인 전 `BLOG_ADMIN` -> 대기 페이지
- `BLOG_MEMBER` -> 본인 소속 블로그

### 발표 멘트

"같은 로그인 성공이라도 사용자의 상태에 따라 이동 화면이 다릅니다. 이 정책이 실제 사용자 경험과 보안에 큰 영향을 줍니다."

---

## 페이지 9. 블로그멤버 글쓰기 정책 (2분)

### 슬라이드 내용

- 소유자 or ACTIVE 멤버만 글쓰기 허용
- 미가입 블로그는 읽기 전용
- 작성자 ID는 세션 기준 강제(위변조 방지)

### 발표 멘트

"UI에서 버튼을 숨기는 것만으로는 보안이 되지 않습니다. 최종 권한 판단은 반드시 서버에서 해야 합니다."

---

## 페이지 10. 슈퍼관리자 정책 기능 (2분)

### 슬라이드 내용

- 관리자 승인/거절
- 블로그·게시판 생성 권한 부여
- 게시판 생성 쿼터 제한
- 이미지 개수/크기 제한
- 관리 차단/프로파일 제한

### 발표 멘트

"PRD에 있는 정책 항목을 시스템 설정값으로 바꾸면 운영 자동화가 됩니다. 사람이 매번 판단하지 않아도 정책으로 제어할 수 있습니다."

---

## 페이지 11. 데이터 모델 설계 포인트 (2분)

### 슬라이드 내용

- `blog_user`: 역할/승인/권한/제한/프로파일
- `blog`: 게시판/이미지 제한 정책
- 정책 컬럼의 기본값 설계 중요

### 발표 멘트

"정책 중심 서비스는 DB 스키마가 곧 제품 정책입니다. 기본값을 어떻게 두느냐가 실제 운영 리스크를 결정합니다."

---

## 페이지 12. 마이그레이션 전략 (2분)

### 슬라이드 내용

- 신규 설치: `01_create_tables.sql`
- 운영 업그레이드: `03_migrate_to_super_admin_model.sql`
- 기존 role 정규화: `ADMIN -> SUPER_ADMIN`, `USER -> BLOG_MEMBER`

### 발표 멘트

"현업에서 더 중요한 것은 '새로 만드는 것'보다 '기존 시스템을 안전하게 바꾸는 것'입니다. 그래서 마이그레이션이 핵심입니다."

---

## 페이지 13. 백엔드 아키텍처 연결 (2분)

### 슬라이드 내용

- Controller -> Service -> Mapper -> DB
- 권한 로직은 Service/Controller에서 서버 검증
- Interceptor로 관리자 경로 보호

### 발표 멘트

"구조를 지키면 변경이 쉬워집니다. 역할 체크, 멤버십 체크, 정책 저장이 계층별로 분리되어야 테스트도 쉬워집니다."

---

## 페이지 14. 화면 설계와 사용자 피드백 (2분)

### 슬라이드 내용

- 관리자 대시보드에서 권한/제한 설정
- 멤버에게 읽기 전용 안내 메시지
- 승인 대기 사용자 안내

### 발표 멘트

"보안은 조용히 막는 것보다 사용자에게 이유를 설명하는 게 중요합니다. 안내 메시지는 UX 품질을 결정합니다."

---

## 페이지 15. 테스트 전략 (2분)

### 슬라이드 내용

- 기능 테스트: 로그인/승인/권한
- 보안 테스트: 위변조/우회 요청
- 회귀 테스트: 기존 기능 영향 확인

### 발표 멘트

"권한 기능은 정상 경로보다 예외 경로 테스트가 더 중요합니다. '하면 된다'보다 '하면 안 되는 게 막힌다'를 검증해야 합니다."

---

## 페이지 16. 수용 기준(AC) 예시 (2분)

### 슬라이드 내용

- 승인 전 관리자 대기 페이지 이동
- 슈퍼관리자만 `/admin/**` 접근
- 가입 블로그 외 글쓰기 차단
- 정책 변경 즉시 DB 반영

### 발표 멘트

"AC는 개발 완료 기준입니다. 모호한 완료 정의를 없애고, 팀 내 합의된 '끝'을 만듭니다."

---

## 페이지 17. 개발 방법론 비교: 워터폴 vs 애자일 (2분)

### 슬라이드 내용

- 워터폴: 안정적 문서, 느린 변경
- 애자일: 빠른 반복, 강한 커뮤니케이션 필요
- 수업 프로젝트 권장: 애자일 + 최소 PRD

### 발표 멘트

"교육 프로젝트에서는 완전한 워터폴보다, 짧은 반복 개발에 PRD를 결합하는 방식이 학습 효과가 높습니다."

---

## 페이지 18. 스프린트 운영 예시 (2분)

### 슬라이드 내용

- 스프린트 1: 인증/역할/마이그레이션
- 스프린트 2: 관리자 정책/권한 UI
- 데일리: 리스크 공유, 우선순위 조정
- 리뷰/회고: 학습 포인트 정리

### 발표 멘트

"2주만 있어도 스프린트 운영이 가능합니다. 중요한 것은 작은 완료 단위를 계속 만드는 것입니다."

---

## 페이지 19. 학생 실습 과제 제안 (2분)

### 슬라이드 내용

- 과제1: 댓글/대댓글 권한 모델 추가
- 과제2: 게시글 비밀번호 열람 정책 구현
- 과제3: 감사 로그 테이블 설계

### 발표 멘트

"오늘 배운 PRD 방식으로 기능을 하나 더 정의하고, DB/백엔드/화면까지 연결해보면 실무 감각이 크게 올라갑니다."

---

## 페이지 20. 결론 및 Q&A (2분)

### 슬라이드 내용

- PRD는 개발 이전의 문서가 아니라 개발 전체의 기준선
- 권한 기능은 서버 검증이 핵심
- 방법론은 도구가 아니라 팀 협업 방식

### 발표 멘트

"좋은 코드는 좋은 요구사항에서 시작합니다. PRD를 제대로 쓰면 구현 속도뿐 아니라 품질과 협업 효율도 함께 올라갑니다. 질문 받겠습니다."

---

## 부록 A. 시간 관리표 (총 40분)

- 1~5페이지: 10분 (도입/배경/PRD 개념)
- 6~12페이지: 14분 (요구사항/권한/데이터/마이그레이션)
- 13~18페이지: 12분 (구현/테스트/방법론/운영)
- 19~20페이지: 4분 (실습 제안/결론)

## 부록 B. 발표 팁

- 기술 설명 70%, 사례/질문 30% 비율 유지
- 어려운 용어는 "정의 -> 예시 -> 코드 반영" 순서로 설명
- 매 5페이지마다 1문장 요약으로 청중 집중 회복
