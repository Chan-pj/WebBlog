# PRD (학생 교육용) - 블로그 플랫폼

## 1. 문서 목적

이 문서는 `webblog` 프로젝트를 기준으로, 학생들이 다음을 이해하도록 돕기 위한 교육용 PRD(Product Requirements Document)입니다.

- PRD가 무엇인지
- 요구사항을 어떻게 제품 기능으로 구조화하는지
- 권한/승인 정책이 시스템 설계에 어떻게 반영되는지
- 어떤 개발 방법론으로 구현/검증/운영하는지

---

## 2. PRD란 무엇인가

PRD는 "무엇을 왜 만들지"를 정의하는 문서입니다.

- **무엇(What)**: 사용자에게 제공할 기능과 동작
- **왜(Why)**: 문제 정의, 목표, 기대 효과
- **어떻게 검증할지(How to validate)**: 성공 지표, 수용 기준(acceptance criteria)

PRD는 코드 설계서가 아니라, 제품의 목표와 요구사항을 팀이 같은 언어로 이해하도록 만드는 기준 문서입니다.

---

## 3. 프로젝트 배경과 문제 정의

### 3.1 배경

학교/수업 환경에서 블로그 플랫폼을 운영할 때 다음 문제가 자주 발생합니다.

- 누구나 관리자 기능에 접근하면 운영 안정성이 떨어짐
- 블로그별 권한 정책이 없으면 데이터 오남용 가능
- 게시판/업로드 정책이 없으면 저장소/트래픽 관리가 어려움

### 3.2 해결하려는 문제

- 사용자 역할(슈퍼관리자/블로그관리자/블로그멤버)에 따라 기능을 분리한다.
- 블로그관리자는 승인 후에만 생성/관리 기능을 사용한다.
- 블로그멤버는 가입한 블로그에서만 글쓰기 가능하게 한다.
- 슈퍼관리자는 정책(생성 권한, 쿼터, 업로드 제한, 차단/제한)을 중앙 통제한다.

---

## 4. 제품 목표

### 4.1 비즈니스 목표

- 안전한 운영 정책을 갖춘 교육용 블로그 플랫폼 제공
- 역할 기반 접근제어(RBAC)와 승인 절차 학습
- 실제 현업 수준의 요구사항 문서화/구현/검증 흐름 경험

### 4.2 사용자 목표

- 블로그멤버: 관심 블로그를 구독하고 읽고, 가입 블로그에서는 글 작성
- 블로그관리자: 승인 후 본인 블로그/게시판 운영
- 슈퍼관리자: 운영정책 설정, 권한 부여, 제한/차단 수행

---

## 5. 범위 정의 (Scope)

### 5.1 In Scope (이번 범위)

- 이메일 로그인
- 카카오 OAuth 로그인
- 회원가입(블로그멤버/블로그관리자 신청)
- 역할 모델: `SUPER_ADMIN`, `BLOG_ADMIN`, `BLOG_MEMBER`
- 블로그관리자 승인/권한/쿼터/제한 관리
- 블로그멤버 글쓰기 권한(가입 블로그에서만 가능)
- 블랙리스트(전역/블로그별 금지어) 기반 게시글 검증

### 5.2 Out of Scope (차기 범위)

- 댓글/대댓글(응답형 게시판)
- 게시글 비밀번호 세분화 열람 정책
- 실제 파일 업로드 저장/이미지 리사이징 파이프라인
- 감사 로그 대시보드/알림 시스템

---

## 6. 이해관계자(Stakeholders)

- **Product Owner(교수/강사)**: 교육 목표/우선순위 결정
- **개발팀(학생)**: 요구사항 구현/테스트
- **운영자(슈퍼관리자 역할)**: 승인/정책/차단 관리
- **최종 사용자(학생 사용자)**: 블로그 열람/작성

---

## 7. 사용자 역할 및 권한 모델

### 7.1 역할 정의

- `SUPER_ADMIN`
  - 블로그관리자 승인/거절
  - 블로그/게시판 생성 권한 부여
  - 게시판 생성 개수 제한
  - 이미지 개수/크기 제한
  - 블랙리스트 정책 적용
  - 블로그관리자 관리 차단/프로파일 제한

- `BLOG_ADMIN`
  - 승인 후 본인 블로그 생성/관리(권한 부여 범위 내)
  - 본인 블로그별 블랙리스트 추가 운영

- `BLOG_MEMBER`
  - 여러 블로그 열람 가능
  - 가입한 블로그에서만 글쓰기 가능
  - 미가입 블로그는 읽기 전용

### 7.2 승인 상태

- `is_approved = false`인 `BLOG_ADMIN`은 대기 화면으로 유도
- 승인 후 관리자 권한 사용 가능

---

## 8. 핵심 사용자 시나리오 (User Stories)

1) 블로그멤버 가입/로그인  
"사용자로서 이메일로 가입하고 로그인하여 블로그를 열람하고 싶다."

2) 블로그관리자 신청  
"사용자로서 블로그관리자로 가입 신청하고 승인 결과를 기다리고 싶다."

3) 슈퍼관리자 승인  
"슈퍼관리자로서 블로그관리자 신청자를 승인하고 생성 권한/쿼터를 설정하고 싶다."

4) 멤버 글쓰기 제어  
"블로그 운영자로서 내 블로그 멤버만 글을 쓰도록 제한하고 싶다."

---

## 9. 기능 요구사항 (Functional Requirements)

### FR-01 인증

- 이메일 로그인 제공
- 카카오 OAuth 로그인 제공
- 세션 기반 인증(`loginUser`)

### FR-02 회원가입

- 가입 유형 선택: `BLOG_MEMBER`, `BLOG_ADMIN`
- `BLOG_ADMIN`은 기본 승인 대기 상태로 생성

### FR-03 권한/승인

- `SUPER_ADMIN` 전용 관리자 화면
- 사용자별 승인/권한/쿼터/제한 값 수정 가능

### FR-04 블로그멤버 글쓰기 정책

- 소유자 또는 ACTIVE 멤버만 해당 블로그에서 글쓰기 허용
- 작성자 ID는 클라이언트 입력이 아니라 세션 사용자로 강제

### FR-05 운영정책

- 게시판 생성 쿼터
- 이미지 업로드 개수/크기 제한 값 관리
- 관리 차단/프로파일 제한

---

## 10. 비기능 요구사항 (Non-Functional Requirements)

- **보안**: 권한 검증은 반드시 서버에서 수행
- **성능**: 권한 체크 API는 단순 조회로 200ms 이내(로컬 기준)
- **가용성**: 정책 컬럼 누락 시 배포 금지(마이그레이션 선행)
- **운영성**: 설정값/환경변수/DB 스키마 문서화
- **확장성**: 역할/정책 컬럼 확장 가능 구조 유지

---

## 11. 데이터 모델 요약

### 11.1 `blog_user` 주요 필드

- 식별: `user_id`, `email`
- 역할: `role`
- 승인/권한: `is_approved`, `can_create_blog`, `can_create_board`, `board_create_quota`
- 정책 제한: `image_upload_limit_count`, `image_size_limit_bytes`
- 통제: `management_blocked`, `profile_restricted`
- 프로파일: `phone_number`, `profile_image_url`, `profile_blog_title`, `profile_etc`

### 11.2 `blog` 주요 필드

- 소유자: `owner_user_id`
- 게시판/업로드 제한: `board_limit`, `image_limit_count`, `image_size_limit_bytes`

---

## 12. 수용 기준 (Acceptance Criteria)

- [ ] `BLOG_ADMIN` 승인 전 로그인 시 대기 화면 이동
- [ ] `SUPER_ADMIN`만 `/admin/**` 접근 가능
- [ ] 대시보드에서 승인/권한/쿼터/제한 저장 후 DB 반영
- [ ] 멤버는 가입한 블로그에서만 글쓰기 가능
- [ ] 작성자 위변조(hidden field) 불가
- [ ] 마이그레이션 후 기존 데이터의 `role`이 새 정책으로 정규화됨

## 13. 성공 지표 (Metrics)

- 승인/권한 변경 반영 성공률 100%
- 권한 없는 글쓰기 시도 차단률 100%
- 관리자 기능 무단 접근 차단률 100%
- 기능 테스트 케이스 통과율 95% 이상

## 14. 개발 방법론 (학생 설명용)

## 14.1 워터폴 vs 애자일

- **워터폴**
  - 단계: 요구사항 -> 설계 -> 구현 -> 테스트 -> 배포
  - 장점: 문서 중심, 범위가 명확
  - 단점: 변경 대응이 느림

- **애자일(스크럼/칸반)**
  - 짧은 반복(스프린트)으로 계획-구현-검증 반복
  - 장점: 피드백 반영이 빠름
  - 단점: 문서화가 약하면 혼선 발생

본 프로젝트 수업에서는 **애자일 + PRD 최소 문서화**를 권장합니다.

### 14.2 권장 실습 프로세스 (2주 예시)

1. PRD 작성 및 리뷰
2. 스토리 분해(작업 단위 정의)
3. DB 변경(마이그레이션) 먼저 적용
4. 백엔드 권한 로직 구현
5. 화면/UX 반영
6. 테스트(단위 + 시나리오)
7. 데모 및 회고

### 14.3 학생 팀 역할 분담 예시

- PO 역할: 요구사항 우선순위/수용기준 관리
- 백엔드: 권한체계, 서비스/매퍼 구현
- 프론트(JSP): 상태 메시지/입력 폼 반영
- QA: 시나리오 테스트, 회귀 테스트

## 15. 구현 전략 (Engineering Plan)

### 15.1 단계별 구현

- Phase 1: 역할/승인 DB 스키마 적용
- Phase 2: 인증/인가 라우팅 보정
- Phase 3: 슈퍼관리자 권한 UI/엔드포인트
- Phase 4: 글쓰기 권한 강제 및 위변조 방지
- Phase 5: 테스트 자동화/문서 보강

### 15.2 기술 부채 관리

- 하드코딩 role 문자열 -> enum 상수화(차기)
- 권한 로직 분산 -> 공통 AuthorizationService로 통합(차기)
- 업로드 제한 정책 -> 파일 업로드 모듈과 연동(차기)

---

## 16. 테스트 전략

### 16.1 테스트 유형

- 단위 테스트: 서비스 권한 체크
- 통합 테스트: 컨트롤러 + DB + 매퍼
- 인수 테스트: 사용자 시나리오 기반 수동 테스트

### 16.2 핵심 테스트 케이스

- 승인 전/후 `BLOG_ADMIN` 로그인 동작
- `SUPER_ADMIN` 이외 `/admin/**` 접근 차단
- 멤버십 유무에 따른 글쓰기 허용/차단
- 관리자 정책값 저장 후 즉시 조회 반영

---

## 17. 운영/배포 고려사항

- 배포 전 `03_migrate_to_super_admin_model.sql` 적용 필수
- 백업 -> 마이그레이션 -> 검증 쿼리 -> 애플리케이션 재기동 순서 준수
- 환경별(개발/운영) 카카오 키/DB 비밀번호 분리 관리

---

## 18. 리스크 및 대응

- **리스크**: 스키마 반영 누락으로 런타임 SQL 오류  
  **대응**: 배포 체크리스트에 마이그레이션 검증 쿼리 필수화

- **리스크**: 클라이언트 조작으로 권한 우회 시도  
  **대응**: 서버에서 세션 사용자 기준으로 최종 검증

- **리스크**: 역할 정책 변경 시 코드 분산  
  **대응**: 권한 정책 클래스로 중앙화(차기 리팩터링)
